API version `2026-10` is a clean break from `2026-09`. It removes every deprecated endpoint and alias, gives every endpoint the same naming, error, query string, and pagination rules, and reshapes the webhook envelope. Version `2026-09` keeps working until its sunset date, October 1, 2027. From that date, requests on `2026-09` fail with `400 API_VERSION_SUNSET`.

You move one piece at a time, and anything you haven't moved yet stays on `2026-09`:

1. [Find what affects you](#find-what-affects-you).
2. [Send the new version on your requests](#send-the-new-version-on-your-requests).
3. [Move your webhook endpoints](#move-your-webhook-endpoints).
4. [Confirm nothing relies on the default](#confirm-nothing-relies-on-the-default).
5. [Switch the organization default](#switch-the-organization-default).

For how versions work, see [API versioning](/api-fundamentals/versioning).

## Upgrade with an AI assistant

To have a coding assistant such as Claude Code, Cursor, or Codex make the changes, give it the following prompt in your repository. The prompt has the full list of changes, and also points the assistant at the Markdown version of this guide for the before-and-after examples:

<Accordion title="Show the upgrade prompt" icon="sparkles">

```text Upgrade prompt
Upgrade this codebase's sajn API integration from API version 2026-09 to
2026-10. The full guide, with before-and-after examples, is here:

  https://docs.sajn.se/upgrading/2026-10.md

Fetch it if you can. Then find every place this codebase calls the sajn API
(https://app.sajn.se/api/v1) or receives sajn webhooks, and apply the changes
below. Change only what the list covers, and keep behavior the same.

VERSION HEADER
- Send "Sajn-Version: 2026-10" on every sajn API request, from one shared
  place such as the HTTP client. Keep it pinned in code.
- When creating webhooks (POST /api/v1/webhooks), send "apiVersion": "2026-10".

DOCUMENTS AND PARTIES
- POST /api/v1/documents: send "parties", never "signers". The response is
  now the full document: read "id" (not "documentId") and "parties[].id"
  (not "parties[].signerId").
- GET /api/v1/documents/{id} returns "fields" only with ?expand=fields.
- The /api/v1/documents/{id}/signers endpoints are removed: use
  /api/v1/documents/{id}/parties and the path parameter {partyId}.
- POST .../parties/{partyId}/remind is removed: use
  POST /api/v1/documents/{id}/reminders with { "partyIds": [...] }, and read
  each party's outcome from "results" (a failure no longer fails the request).
- GET /api/v1/documents/{id}/download?fileType=X is removed: use
  GET /api/v1/documents/{id}/download/X.
- Role "ACCEPTOR" is rejected: use "SIGNER".
- The externalId filter on GET /api/v1/documents is an exact, case-sensitive
  match. Use "query" for partial matches.

NAMING
- signerId -> partyId, signerName -> partyName, signerEmail -> partyEmail
  (signatures, reminders), originalSigner(Id)/delegateSigner(Id) ->
  originalParty(Id)/delegateParty(Id) (delegations), respondentSignerId ->
  respondentPartyId (forms), and the body of PUT /api/v1/forms/{id}/respondent
  takes "partyId".
- Inside fieldMeta (placed fields, FORM subfields, upsert, initialFields,
  blocks): signerId -> partyId, selectionSignerId -> selectionPartyId,
  visibilityRule.customInputId -> visibilityRule.customFieldId. A request
  that still sends an old name inside fieldMeta or upsert fails with 400.
  GET /api/v1/documents/{id}/field-values returns "partyId", and
  "productTables" on GET /api/v1/documents/{id} returns "selectionPartyId".
- ssn -> nationalId (parties, template parties, contacts, POST /sajn-id),
  ssnDisplayMode -> nationalIdDisplayMode, match method SSN -> NATIONAL_ID.
- customFields[].customInputId -> customFields[].customFieldId on document
  create and update; document categories return "customFieldIds".
- BANKID -> SE_BANKID and BANKID_BEFORE_SIGNING -> SE_BANKID_BEFORE_SIGNING,
  in requests, responses, and stored values such as saved settings.
- Member status values are ACTIVE, INACTIVE, ALL; login session status values
  are PENDING, COMPLETED, FAILED, EXPIRED.
- The event types DOCUMENT_OPENED, DOCUMENT_RECREATED, WORKFLOW_STARTED,
  WORKFLOW_COMPLETED, and WORKFLOW_FAILED are removed from the events and
  webhook deliveries endpoints; an "event" filter naming one returns 400. Use
  DOCUMENT_PARTY_OPENED and DOCUMENT_MODIFIED instead.

FIELDS
- POST .../fields returns { "fields": [...] } with each field in the
  GET .../fields/{fieldId} shape; read the document or template ID from each
  field. PATCH on a field returns the field (no "message"). DELETE returns
  { "id", "deleted": true }.

QUERY STRINGS AND PAGINATION
- Send query values as plain strings, never JSON-encoded: externalId=12345,
  archived=false. Multi-value filters take a comma-separated list or repeated
  parameters. An unknown query parameter now returns 400, so remove any
  parameter the endpoint doesn't document.
- Renames: GET /templates search -> query; GET /documents/{id}/chat
  limit -> perPage; GET /events since/until -> createdAfter/createdBefore
  (createdBefore is inclusive); GET /sajn-id dateFrom/dateTo ->
  createdAfter/createdBefore (no default seven-day window anymore).
- Paginate every list by passing "nextCursor" as "cursor" until
  "hasNextPage" is false. GET /companies is paginated, and
  GET /companies/{id} returns the company without a "company" wrapper.

ERRORS
- Every error body is { code, message, requestId, userMessage?, issues?,
  requiredScopes?, grantedScopes? }. Branch on "code", never on the status or
  the message. Show "userMessage" (Swedish) to end users when present.
  "requestId" replaces "errorId" and matches the Sajn-Request-Id header.
  Each entry in "issues" has a "code", such as INVALID_FORMAT.
- Code renames: INVALID_REQUEST, INVALID_BODY, VALIDATION_ERROR ->
  VALIDATION_FAILED; FORBIDDEN -> PERMISSION_DENIED, INSUFFICIENT_SCOPE,
  PLAN_REQUIRED, or ACCOUNT_INACTIVE; TOO_MANY_REQUESTS -> RATE_LIMITED or
  DAILY_QUOTA_EXCEEDED; idempotency conflicts -> IDEMPOTENCY_KEY_REUSED or
  IDEMPOTENCY_KEY_IN_USE.
- Status changes: monthly send limit 400 -> 403 LIMIT_EXCEEDED; deactivated
  user 401 -> 403 ACCOUNT_INACTIVE; locked template 401 -> 400 INVALID_STATE.

LIMITS
- GET /api/v1/limits: read signatures.SE_BANKID (not bankIdSignatures) and
  aiBudgetOre/aiSpentOre/aiSpentOreSigner (not aiTokens/aiTokensSigner).
  quota.additionalBankidCost, quota.smsCost, and additionalCosts are removed.

WEBHOOK RECEIVERS (only for endpoints you move to 2026-10)
- The delivery body is { id, event, createdAt, apiVersion, payload }.
  Deduplicate on "id"; "createdAt" is when the event happened.
  "webhookEndpoint" is removed.
- The X-Sajn-Secret header is gone: verify the X-Sajn-Signature HMAC instead.
- Document payloads use "name" (not "title"); security payloads use
  "documentName" (not "documentTitle"); party "email" can be null;
  productTables use "selectionPartyId"; "signers" is removed (use "parties").
  DOCUMENT_ARCHIVE_UPLOADED no longer includes "s3Key".
- DOCUMENT_PARTY_AUTH_FAILED is { document, party, method, hintCode,
  failedAt } with method names like SE_BANKID. DOCUMENT_PARTY_DELEGATED is
  { document, party, delegation: { id, delegate, reason, delegatedAt } }.
- The webhook "secret" is returned only on create and on a PATCH that sets a
  new one. Store it at creation.

WHEN YOU'RE DONE
- Update types, fixtures, mocks, tests, and comments to the new shapes.
- List every change you made, and anything you couldn't migrate with
  certainty, such as data stored with old values (BANKID, signerId) that a
  human needs to review.
```

</Accordion>

Review the changes, then run your tests against a sandbox organization with `Sajn-Version: 2026-10` before you switch production traffic.

## Before you begin

- An API key with access to the workspace you integrate with.
- A test environment, such as a [sandbox](/get-started/sandbox) organization, where you can run your integration against `2026-10`.

## Find what affects you

Go through [What to change in your code](#what-to-change-in-your-code) and list each endpoint, field, query parameter, and webhook event your integration uses that a change affects. The [changelog](/upgrading/changelog) has the complete list of changes.

These changes affect almost every integration:

- [`POST /api/v1/documents` returns the full document](#create-document-response), with the ID in `id` instead of `documentId`.
- [Errors have one shape](#errors), with `code` from a closed list.
- [Query values are plain strings](#query-strings), and an unknown query parameter returns `400`.
- [The webhook envelope](#webhook-envelope) has an event `id` and no `webhookEndpoint`.
- [Signer names become party names](#party-ids), including `signerId` inside `fieldMeta`.

## Send the new version on your requests

1. In your test environment, send `Sajn-Version: 2026-10` on every request:

   ```bash
   curl https://app.sajn.se/api/v1/documents \
     -H "Authorization: Bearer API_KEY" \
     -H "Sajn-Version: 2026-10"
   ```

   Replace `API_KEY` with your API key.

2. Update your code for each change that affects it, and run your tests against `2026-10`.
3. Deploy the change to production.

The header takes precedence over the organization default, so your organization default stays on `2026-09` and other integrations on the same organization aren't affected.

We recommend keeping the `Sajn-Version` header in your code permanently. Your integration then never depends on the organization default.

## Move your webhook endpoints

A webhook endpoint keeps its own version, so moving your requests doesn't change your webhook payloads.

To move an endpoint without dropping events, run a second endpoint next to it:

1. Create a second endpoint for the same URL or a new one, with `"apiVersion": "2026-10"` and the same events:

   ```bash
   curl -X POST https://app.sajn.se/api/v1/webhooks \
     -H "Authorization: Bearer API_KEY" \
     -H "Sajn-Version: 2026-10" \
     -H "Content-Type: application/json" \
     -d '{
       "webhookUrl": "https://example.com/webhooks/sajn-2026-10",
       "eventTriggers": ["DOCUMENT_SIGNED", "DOCUMENT_COMPLETED"],
       "apiVersion": "2026-10"
     }'
   ```

   Store the `secret` from the response. On `2026-10`, it's returned only when you create the endpoint or set a new secret.

2. Verify that your receiver handles the `2026-10` deliveries. Each delivery carries its version in the `Sajn-Version` header and the `apiVersion` field, so a receiver on one URL can tell the two endpoints' deliveries apart.
3. Delete the old endpoint with `DELETE /api/v1/webhooks/{id}`.

While both endpoints exist, every event is delivered twice, once per version. A `2026-09` delivery has no event `id`, and `X-Sajn-Delivery` differs between endpoints, so make your handler safe to run twice for one event. For example, check the document's current status before you act on it.

If your receiver already accepts both the `2026-09` and the `2026-10` payloads, you can upgrade the endpoint in place instead. Send `{"apiVersion": "2026-10"}` in a `PATCH /api/v1/webhooks/{id}` request. Every delivery after the change uses `2026-10`, including retries of earlier events.

## Confirm nothing relies on the default

1. In the [dashboard](https://app.sajn.se), go to **Inställningar > Utvecklare**.
2. In the **API-version** section, check the **Anrop de senaste 72 timmarna** table. The **Vald via** column shows whether requests chose their version with the header (**Header**) or relied on the default (**Organisationens standard**).

The table covers only the last 72 hours. If you have jobs that run less often, check the table again after they've run.

If `2026-09` requests from **Organisationens standard** remain, find the integration that sends them before you continue. Either update it for `2026-10`, or make it send `Sajn-Version: 2026-09` until you do.

## Switch the organization default

In the **API-version** section, select `2026-10` in the version list, and then click **Byt version**. Requests without the `Sajn-Version` header use `2026-10` from then on.

Switching the default doesn't change the version of existing webhook endpoints. New webhook endpoints created without `apiVersion` get `2026-10`.

## What to change in your code

Each section shows a `2026-09` request or response, then the same one on `2026-10`. Examples are shortened to the fields that matter.

### Documents and parties

#### Create document response

`POST /api/v1/documents` returns the created document in the same shape as `GET /api/v1/documents/:id`, without `fields`. Read the document ID from `id`, and each party ID from `parties[].id`.

In `2026-09`, the response is a summary:

```json
{
  "documentId": "cm9doc1a2b3c4d5e6f7g8h9i0",
  "externalId": "order-1042",
  "expiresAt": null,
  "signers": [{ "signerId": "cm9pty1a2b3c4d5e6f7g8h9i0", "name": "Alex Berg" }],
  "parties": [
    {
      "signerId": "cm9pty1a2b3c4d5e6f7g8h9i0",
      "name": "Alex Berg",
      "email": "alex@example.com",
      "role": "SIGNER",
      "signingOrder": null,
      "type": "INDIVIDUAL",
      "companyName": null,
      "companyRole": null,
      "companyOrgNumber": null,
      "country": null,
      "contactId": null
    }
  ]
}
```

In `2026-10`, the response is the document:

```json
{
  "id": "cm9doc1a2b3c4d5e6f7g8h9i0",
  "name": "Employment contract",
  "status": "DRAFT",
  "externalId": "order-1042",
  "expiresAt": null,
  "createdAt": "2026-10-01T09:00:00.000Z",
  "updatedAt": "2026-10-01T09:00:00.000Z",
  "completedAt": null,
  "documentMeta": { "subject": null, "signingOrder": "PARALLEL" },
  "parties": [
    {
      "id": "cm9pty1a2b3c4d5e6f7g8h9i0",
      "name": "Alex Berg",
      "email": "alex@example.com",
      "role": "SIGNER",
      "type": "INDIVIDUAL",
      "signingStatus": "NOT_SIGNED",
      "requiredSignature": "SE_BANKID"
    }
  ],
  "tags": [],
  "customFields": [],
  "productTables": []
}
```

`GET /api/v1/documents/:id` also leaves out `fields`. To get them, pass `expand=fields`.

#### Parties instead of signers

Send `parties` instead of `signers` on `POST /api/v1/documents`, and `partyIds` instead of `signerIds` on `POST /api/v1/documents/:id/reminders`. The `ACCEPTOR` role is rejected; send `SIGNER`. Responses and document webhook payloads no longer include `signers`. For a walkthrough, see [Migrating from signers to parties](/upgrading/migrate-signers-to-parties).

#### Removed endpoints

The following endpoints return `404 NOT_FOUND` on `2026-10`:

| Removed endpoint | Use instead |
|------------------|-------------|
| `POST /api/v1/documents/:id/signers` | `POST /api/v1/documents/:id/parties` |
| `GET /api/v1/documents/:id/signers` | `GET /api/v1/documents/:id/parties` |
| `GET`, `PATCH`, or `DELETE /api/v1/documents/:id/signers/:signerId` | The same method on `/api/v1/documents/:id/parties/:partyId` |
| `POST /api/v1/documents/:id/signers/:signerId/remind` | `POST /api/v1/documents/:id/reminders` |
| `POST /api/v1/documents/:id/parties/:partyId/remind` | `POST /api/v1/documents/:id/reminders` |
| `GET /api/v1/documents/:id/download?fileType=SIGNED` | `GET /api/v1/documents/:id/download/SIGNED` |

`POST /api/v1/documents/:id/reminders` takes a list of parties and reports each party's outcome in `results`, instead of failing the whole request:

```json
{
  "partyIds": ["cm9pty1a2b3c4d5e6f7g8h9i0"],
  "channel": "EMAIL"
}
```

The response is similar to the following:

```json
{
  "sent": 1,
  "skipped": 0,
  "failed": 0,
  "results": [
    {
      "partyId": "cm9pty1a2b3c4d5e6f7g8h9i0",
      "partyEmail": "alex@example.com",
      "partyName": "Alex Berg",
      "status": "SENT",
      "reason": null
    }
  ]
}
```

#### Exact externalId filter

The `externalId` filter on `GET /api/v1/documents` matches the whole value, case-sensitively. In `2026-09`, it matched any document whose external ID contained the value, ignoring case. For a partial match, use `query`.

### Fields

#### Party IDs

Every request and response names a party `partyId`, also inside `fieldMeta`. This includes the boxes in a PDF field's `placedFields`, the `upsert` list on the placed-fields endpoints, FORM subfields, and `initialFields` on `POST /api/v1/templates`.

In `2026-09`, a box in `placedFields` names its party `signerId`:

```json
{
  "id": "sign-alex",
  "kind": "input",
  "inputType": "signature",
  "page": 0,
  "rect": { "x": 72, "y": 640, "width": 180, "height": 48 },
  "fillSource": "signer",
  "signerId": "cm9pty1a2b3c4d5e6f7g8h9i0"
}
```

In `2026-10`, it's `partyId`:

```json
{
  "id": "sign-alex",
  "kind": "input",
  "inputType": "signature",
  "page": 0,
  "rect": { "x": 72, "y": 640, "width": 180, "height": 48 },
  "fillSource": "signer",
  "partyId": "cm9pty1a2b3c4d5e6f7g8h9i0"
}
```

The same rename applies elsewhere in `fieldMeta`:

- A PRODUCT_TABLE field takes `selectionPartyId` instead of `selectionSignerId`. `productTables` on `GET /api/v1/documents/:id` and on webhooks returns `selectionPartyId` too.
- A `visibilityRule` takes `customFieldId` instead of `customInputId`.
- `GET /api/v1/documents/:id/field-values` returns `partyId` instead of `signerId`.

A request that still sends `signerId`, `selectionSignerId`, or `customInputId` inside `fieldMeta` or `upsert` fails with `400 VALIDATION_FAILED`.

#### Field endpoint responses

The field endpoints on documents and templates return the field in the same shape as `GET /api/v1/documents/:id/fields/:fieldId`:

| Request | `2026-09` response | `2026-10` response |
|---------|--------------------|--------------------|
| `POST /api/v1/documents/:id/fields` or `POST /api/v1/templates/:id/fields` | `{ fields, documentId }` or `{ fields, templateId }` | `{ fields }`. Read the document or template ID from each field. |
| `PATCH` on `/fields/:fieldId` | `id`, `type`, `position`, `fieldMeta`, and the document or template ID, plus `message` for a FORM subfield addressed with `key:` | The updated field, without `message` |
| `DELETE` on `/fields/:fieldId` | The deleted field's `id`, `type`, `position`, `fieldMeta`, and the document or template ID | `{ "id": "...", "deleted": true }` |

To keep a field's content after you delete it, read the field before you delete it.

### Naming

#### Renamed fields and values

The following names change in requests, responses, and webhook payloads. A request body that still uses an old name or value fails with `400 VALIDATION_FAILED`.

| `2026-09` | `2026-10` | Where |
|-----------|-----------|-------|
| `ssn` | `nationalId` | Parties, template parties, contacts, `POST /api/v1/sajn-id` |
| `ssnDisplayMode` | `nationalIdDisplayMode` | `documentMeta`, `templateMeta` |
| `SSN` | `NATIONAL_ID` | `identity.match.method` on `GET /api/v1/documents/:id/signatures` |
| `customInputId` | `customFieldId` | `customFields[]` on `POST /api/v1/documents` and `PATCH /api/v1/documents/:id` |
| `customInputIds` | `customFieldIds` | `GET /api/v1/document-categories` |
| `BANKID` | `SE_BANKID` | `requiredSignature` |
| `BANKID_BEFORE_SIGNING` | `SE_BANKID_BEFORE_SIGNING` | `twoStepVerification`, `accessVerification` |
| `signerId`, `signerName` | `partyId`, `partyName` | `GET /api/v1/documents/:id/signatures` |
| `signerId`, `signerEmail`, `signerName` | `partyId`, `partyEmail`, `partyName` | The reminder endpoints |
| `originalSignerId`, `delegateSignerId`, `originalSigner`, `delegateSigner` | `originalPartyId`, `delegatePartyId`, `originalParty`, `delegateParty` | `GET /api/v1/documents/:id/delegations` |
| `respondentSignerId` | `respondentPartyId` | The form endpoints |
| `signerId` | `partyId` | `PUT /api/v1/forms/:id/respondent` request body |
| `active`, `inactive` | `ACTIVE`, `INACTIVE` | Member `status`, and the `status` filter on `GET /api/v1/members`, which also takes `ALL` |
| `pending`, `complete`, `failed`, `expired` | `PENDING`, `COMPLETED`, `FAILED`, `EXPIRED` | `status` on `GET /api/v1/login/sessions/:id` |

For example, a party in `2026-09`:

```json
{
  "name": "Alex Berg",
  "email": "alex@example.com",
  "ssn": "199001011234",
  "requiredSignature": "BANKID",
  "twoStepVerification": "BANKID_BEFORE_SIGNING"
}
```

The same party in `2026-10`:

```json
{
  "name": "Alex Berg",
  "email": "alex@example.com",
  "nationalId": "199001011234",
  "requiredSignature": "SE_BANKID",
  "twoStepVerification": "SE_BANKID_BEFORE_SIGNING"
}
```

#### Removed event types

The events API and the webhook deliveries endpoint no longer list `DOCUMENT_OPENED`, `DOCUMENT_RECREATED`, `WORKFLOW_STARTED`, `WORKFLOW_COMPLETED`, or `WORKFLOW_FAILED`, because sajn never emits them. An `event` filter that names one returns `400`. To track a party opening a document, use `DOCUMENT_PARTY_OPENED`. To track changes to a sent document, use `DOCUMENT_MODIFIED`.

### Query strings and pagination

#### Query strings

Send query values as plain strings. In `2026-09`, the API JSON-decoded each value, so some clients sent strings in quotes:

```bash
GET /api/v1/documents?externalId=%22order-1042%22&archived=false
```

In `2026-10`, send the value as is. A quoted value matches the quotes literally:

```bash
GET /api/v1/documents?externalId=order-1042&archived=false
```

The following rules apply to every query parameter:

- Booleans take `true` or `false`.
- Dates take an ISO 8601 date, such as `2026-10-01`, or a date-time, such as `2026-10-01T08:00:00Z`. A date-time without an offset is UTC.
- Filters that take several values, such as `status`, `tagId`, and `event`, take a comma-separated list (`status=PENDING,COMPLETED`) or a repeated parameter (`status=PENDING&status=COMPLETED`).

An unknown query parameter returns `400 VALIDATION_FAILED` instead of being ignored, so a misspelled filter fails instead of returning every result:

```json
{
  "code": "VALIDATION_FAILED",
  "message": "Unrecognized key: \"staus\"",
  "requestId": "req_V1StGXR8Z5jdHi6BmyT2",
  "issues": [
    { "path": "", "code": "UNRECOGNIZED_KEY", "message": "Unrecognized key: \"staus\"" }
  ]
}
```

#### Renamed query parameters

| Endpoint | `2026-09` | `2026-10` |
|----------|-----------|-----------|
| `GET /api/v1/templates` | `search` | `query` |
| `GET /api/v1/documents/:id/chat` | `limit` | `perPage` |
| `GET /api/v1/events` | `since`, `until` | `createdAfter`, `createdBefore` |
| `GET /api/v1/sajn-id` | `dateFrom`, `dateTo` | `createdAfter`, `createdBefore` |

`createdBefore` includes its boundary, whereas `until` excluded it. `GET /api/v1/sajn-id` returns every ID check when you omit `createdAfter`; in `2026-09`, it returned only the last seven days.

#### Pagination

Every page-based list returns `hasNextPage` and `nextCursor`. In `2026-09`, most lists returned only the page count:

```json
{
  "contacts": [],
  "total": 87,
  "totalPages": 5
}
```

In `2026-10`:

```json
{
  "contacts": [],
  "total": 87,
  "totalPages": 5,
  "hasNextPage": true,
  "nextCursor": "eyJwIjoyfQ"
}
```

To get the next page, pass `nextCursor` as `cursor`, keep the other parameters unchanged, and stop when `hasNextPage` is `false`. `page` and `perPage` keep working.

`GET /api/v1/companies` is paginated like `GET /api/v1/contacts`: it takes `page`, `perPage`, `cursor`, and `query`, and returns `total`, `totalPages`, `hasNextPage`, and `nextCursor`. In `2026-09`, it returned every company in one response. `GET /api/v1/companies/:id` returns the company object itself; in `2026-09`, it was wrapped in `{ "company": { } }`.

### Errors

Every error response has the same shape, with `code` from a closed list. For every code, see [Errors](/api-fundamentals/errors).

In `2026-09`, a validation error looks like the following:

```json
{
  "message": "Invalid email address",
  "code": "INVALID_REQUEST",
  "issues": [{ "path": "parties.0.email", "message": "Invalid email address" }]
}
```

In `2026-10`, the same error looks like the following:

```json
{
  "code": "VALIDATION_FAILED",
  "message": "Invalid email address",
  "requestId": "req_V1StGXR8Z5jdHi6BmyT2",
  "issues": [{ "path": "parties.0.email", "code": "INVALID_FORMAT", "message": "Invalid email address" }]
}
```

To update your error handling, do the following:

- Branch on `code`. It's always present.
- Show your users `userMessage`, which holds the Swedish text when one exists. In `2026-09`, that text was in `message`.
- Log `requestId` instead of `errorId`. It matches the `Sajn-Request-Id` response header.
- Map the old codes to the new ones:

  | `2026-09` code | `2026-10` code |
  |----------------|----------------|
  | `INVALID_REQUEST`, `INVALID_BODY`, `VALIDATION_ERROR` | `VALIDATION_FAILED` |
  | `FORBIDDEN` | `PERMISSION_DENIED`, `INSUFFICIENT_SCOPE`, `PLAN_REQUIRED`, or `ACCOUNT_INACTIVE` |
  | `TOO_MANY_REQUESTS` | `RATE_LIMITED` or `DAILY_QUOTA_EXCEEDED` |
  | `DUPLICATE_EXTERNAL_ID` | `ALREADY_EXISTS` |
  | `EXPIRED_CODE` | `EXPIRED` |
  | `RESPONSIBLE_PERSON_REQUIRED`, `WORKSPACE_REQUIRED` | `ACCOUNT_SETUP_REQUIRED` |
  | `INVALID_REQUEST` or `ALREADY_EXISTS` for a reused `Idempotency-Key` | `IDEMPOTENCY_KEY_REUSED` (400) or `IDEMPOTENCY_KEY_IN_USE` (409) |

- Expect the following status changes:
  - Sending a document past the monthly limit returns `403 LIMIT_EXCEEDED` instead of `400`.
  - A token whose user is deactivated returns `403 ACCOUNT_INACTIVE` instead of `401`.
  - Editing a locked template returns `400 INVALID_STATE` instead of `401`.

### Webhooks

#### Webhook envelope

The delivery body has an event `id`, and `createdAt` is when the event happened. In `2026-09`, `createdAt` is when the attempt was sent, and the body repeats the endpoint URL:

```json
{
  "event": "DOCUMENT_SIGNED",
  "payload": { "id": "cm9doc1a2b3c4d5e6f7g8h9i0", "title": "Employment contract" },
  "createdAt": "2026-10-01T12:00:04.512Z",
  "webhookEndpoint": "https://example.com/webhooks/sajn",
  "apiVersion": "2026-09"
}
```

In `2026-10`:

```json
{
  "id": "cm9evt1a2b3c4d5e6f7g8h9i0",
  "event": "DOCUMENT_SIGNED",
  "createdAt": "2026-10-01T12:00:00.000Z",
  "apiVersion": "2026-10",
  "payload": { "id": "cm9doc1a2b3c4d5e6f7g8h9i0", "name": "Employment contract" }
}
```

`id` and `createdAt` stay the same across retries and replays, so deduplicate on `id`. To fetch the event later, pass `id` to `GET /api/v1/events/:id`.

The `X-Sajn-Secret` header, which carried the endpoint secret in plain text, isn't sent. Verify deliveries with the `X-Sajn-Signature` header. For how, see [Webhooks](/webhooks/overview).

#### Document payloads

Document payloads use the names the REST API uses:

- The document has `name` instead of `title`, and adds `expiresAt` and `completedAt`.
- Each party adds `role` and `signedAt`, and a party without an email address has `"email": null` instead of `""`.
- The document has no `signers` array; read `parties`.
- In `productTables`, `selectionPartyId` replaces `selectionSignerId`.
- `SECURITY_DOCUMENT_DOWNLOADED` and `SECURITY_SIGNATURE_IDENTITY_ACCESSED` have `documentName` instead of `documentTitle`.
- `DOCUMENT_ARCHIVE_UPLOADED` no longer includes `s3Key`.

#### Party events

Every party event has a `{ document, party }` payload. In `2026-09`, `DOCUMENT_PARTY_AUTH_FAILED` and `DOCUMENT_PARTY_DELEGATED` have a flat payload instead:

```json
{
  "documentId": "cm9doc1a2b3c4d5e6f7g8h9i0",
  "documentName": "Employment contract",
  "signerId": "cm9pty1a2b3c4d5e6f7g8h9i0",
  "method": "BANKID",
  "hintCode": "userCancel",
  "failedAt": "2026-10-01T12:00:00.000Z"
}
```

In `2026-10`, `DOCUMENT_PARTY_AUTH_FAILED` has the full document and party, and `method` uses the eID scheme name:

```json
{
  "document": { "id": "cm9doc1a2b3c4d5e6f7g8h9i0", "name": "Employment contract", "parties": [] },
  "party": { "id": "cm9pty1a2b3c4d5e6f7g8h9i0", "name": "Alex Berg", "email": "alex@example.com" },
  "method": "SE_BANKID",
  "hintCode": "userCancel",
  "failedAt": "2026-10-01T12:00:00.000Z"
}
```

`DOCUMENT_PARTY_DELEGATED` moves the delegation into `delegation`. Read the delegating party from `party` instead of `originalSigner`:

```json
{
  "document": { "id": "cm9doc1a2b3c4d5e6f7g8h9i0", "name": "Employment contract", "parties": [] },
  "party": { "id": "cm9pty1a2b3c4d5e6f7g8h9i0", "name": "Alex Berg", "email": "alex@example.com" },
  "delegation": {
    "id": "cm9dlg1a2b3c4d5e6f7g8h9i0",
    "delegate": { "name": "Kai Lund", "email": "kai@example.com", "phone": null },
    "reason": "On parental leave",
    "delegatedAt": "2026-10-01T12:00:00.000Z"
  }
}
```

In `2026-09`, the same event has `documentId`, `documentName`, `signerId`, `originalSigner`, `delegate`, `reason`, `delegationId`, and `delegatedAt` at the top level.

#### Webhook secret

`GET /api/v1/webhooks` and `GET /api/v1/webhooks/:id` no longer return `secret`. It's returned only by `POST /api/v1/webhooks`, and by `PATCH /api/v1/webhooks/:id` when the request sets a new secret. Store the secret when you create the endpoint. To replace a lost secret, send a new `secret` in a `PATCH /api/v1/webhooks/:id` request.

### Limits

`GET /api/v1/limits` no longer returns the following fields:

- `bankIdSignatures`: read `signatures.SE_BANKID` instead.
- `aiTokens` and `aiTokensSigner`: read `aiBudgetOre`, `aiSpentOre`, and `aiSpentOreSigner` instead.
- `quota.additionalBankidCost`, `quota.smsCost`, and `additionalCosts`: they always returned `0`. To track use beyond your plan, compare `usage` with `quota`. The prepaid credit that pays for it is in `balance`.
